2.1資料理解的目的

模型訓練前必須先確認每個欄位的意義、資料型態、缺失情況，以及是否可能造成 Target Leakage（目標洩漏）或 Data Leakage（資料洩漏）。高分模型若使用了不應取得的資訊，並不代表真正具有辨識能力。

資料規模→欄位定義→資料品質→分布與異常→Success 比例→第三章處理策略
本章核心問題：11,500 筆 Google Play App 資料包含哪些資訊？哪些欄位可繼續使用，哪些欄位必須先轉換、排除或進一步稽核？

2.5缺失值與資料品質

15 個原始欄位中，只有 Rating 存在 NaN：5,377 筆，占 46.76%；其餘 14 欄 NaN 為 0。

NaN = 0 不代表可直接建模：Size、Current Ver、Android Ver 等欄位仍可能含有 Varies with device 等特殊內容，需要格式轉換或特別處理。

2.6重複資料與同名 App

Duplicate Row（完全重複列）

0 筆。原始資料沒有整列完全相同的重複紀錄。

Duplicate App Name（同名 App）

App 僅 2,377 個唯一名稱；同名紀錄其他欄位仍可能不同，不能直接刪除。

切分風險：若同一 App 的相似紀錄同時落入 Train / Test，可能形成 Group Leakage 或 Entity Leakage，造成測試結果被高估；此問題需在第三章繼續稽核。

2.7Target Success 的 Exploratory Data Analysis（探索式資料分析）

16.93%Success = 1

Success = 1：Installs ≥ 10,000，共 1,947 筆（16.93%）。

Success = 0：Installs < 10,000，共 9,553 筆（83.07%）。

Imbalance Ratio（不平衡比例）：Class 0 : Class 1 ≈ 4.91 : 1，後續模型評估必須特別關注少數類別。

2.8為什麼 Accuracy（準確率）不足以代表模型好壞

Class 0 已占 83.07%。若模型把所有 App 都預測為 Class 0，即使完全無法辨識 Success = 1，Accuracy（準確率）仍可達 83.07%。

Precision / Recall

觀察少數類別預測品質與找回能力。

F1 / ROC-AUC

補充分類平衡與整體排序能力。

PR-AUC / Confusion Matrix

在類別不平衡情境中特別重要，並直接檢視 TP、FP、FN、TN。

評估重點：後續尤其關注 Class 1 的 Recall（召回率）與 F1-score（F1 分數），而不是只看 Accuracy。

2.9Target Leakage（目標洩漏）的初步判斷

Installs 必須排除：Success 本身由 Installs 是否達 10,000 建立；建立 Y 後若仍把 Installs 放入 X，模型等於直接取得答案。

Rating 與 Reviews 則必須依 Prediction Time（預測時點）與系統用途進一步判斷，不得只因可能提高模型分數就直接保留。

2.11本章小結

EDA 確認原始資料為 11,500 筆、15 欄，且沒有完全重複列。Rating 是唯一存在 NaN 的欄位，缺失率 46.76%；Reviews 呈現明顯右偏長尾；Size、Last Updated、Android Ver 等欄位雖無 NaN，仍需轉換後才能建模。

Success 的 Class 0 / Class 1 分別為 83.07% / 16.93%，Imbalance Ratio 約 4.91 : 1，因此後續不能只使用 Accuracy（準確率）評估。Installs 必須排除，Rating 與 Reviews 則留待第三章完成 Leakage / Proxy Audit（資料洩漏／代理變數稽核）。
